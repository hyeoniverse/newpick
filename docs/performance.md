# 모바일 성능 (#292)

휴대폰에서 첫 화면이 늦게 보이던 것을 재고 고친 기록입니다. 목표는 **모바일 LCP 2.5초 이하**(Core Web Vitals "좋음")였습니다.

- 측정값의 다른 기록(번들 · 테스트 · 취약점): [baseline.md](baseline.md)
- 바꾸기 전 · 후 화면 비교: [visual-diff.md](visual-diff.md)

## 결과

운영(`newpick.hyeoniverse.com`), 모바일, 화면마다 3번 재서 점수 중앙값인 한 번의 값입니다.

| 화면 | 처음 (점수 · LCP) | 지금, 계산으로 흉내 (점수 · LCP) | 지금, 실제로 느리게 (점수 · LCP) |
| --- | --- | --- | --- |
| 홈 `/` | 73 · 7.1초 | **94 · 3.0초** | – · **2.0초** |
| 목록 `/articles` | 81 · 5.0초 | **90 · 3.7초** | 95 · **1.8초** |
| 상세 `/articles/detail/92` | 82 · 4.6초 | **99 · 1.0초** | 96 · **1.8초** |
| 상세 `/articles/detail/60` | 90 · 3.6초 | 91 · 3.5초 | 97 · **1.8초** |
| 소개 `/about` | 84 · 4.1초 | **99 · 1.2초** | 95 · **1.8초** |
| 태그 `/tags` | 100 · 1.2초 | 100 · 1.2초 | 98 · 1.7초 |

- CLS는 모든 화면 0.05 이하, TBT는 200ms 이하입니다.
- 홈의 "실제로 느리게"는 점수가 없습니다. 흐르는 사진 띠가 화면에 들어오는 사진을 계속 받아, Lighthouse가 기다리는 "네트워크가 조용한 때"가 오지 않아 TBT를 계산하지 못합니다(`NO_TTI_NETWORK_IDLE_PERIOD`). LCP는 잡힙니다.
- 두 측정 방식의 차이는 아래 [측정 방법](#측정-방법)에 있습니다. **실제로 느리게**가 실제 휴대폰 Chrome이 기록하는 값에 가깝고, 모든 화면이 목표 안입니다. **계산으로 흉내**는 같은 화면에서도 크게 흔들립니다(상세 60: 실제 LCP는 3번 모두 0.6~0.9초인데 계산 값은 1.0초 · 3.5초 · 3.5초).

### 마이페이지 (로그인 필요)

로컬 운영 빌드 + 로컬 api, 테스트 사용자 쿠키, 휴대폰 412px, "실제로 느리게"와 같은 조건에서 브라우저가 기록한 값입니다(#292는 3번, #307은 5번 중앙값).

| 화면 | LCP: 처음 → #292 → **#307** | CLS: 처음 → #292 → **#307** |
| --- | --- | --- |
| `/mypage` | 3.9초 → 3.4초 → **0.74초** | 0.127 → 0 → **0** |
| `/mypage?tab=bookmarks` | 3.9초 → 3.4초 → **0.75초** | 0.186 → 0.059 → **0** |
| `/mypage?tab=highlights` | | 0.073 → **0** |

- **#307**: 프로필을 JS가 다 돈 뒤 브라우저에서 받아 그리던 것을, 서버(`page.tsx`)가 로그인 쿠키로 받아 첫 HTML에 넣습니다(`api/serverProfile.ts`). 프로필 사진(LCP)이 JS를 기다리지 않습니다. `/mypage`는 정적(○) → 동적(ƒ)이 되고, Next가 `Cache-Control: private, no-store`를 붙여 다른 사람의 프로필이 캐시로 섞이지 않습니다. 서버에서 1.5초 안에 못 받거나 거절되면 예전처럼 브라우저가 받아 그립니다.
- 탭 목록은 폴더 줄 · '요즘 관심 있게 본 주제'까지 다 받은 뒤에 그립니다. 목록이 먼저 오면 이 둘이 뒤늦게 늘어나며 아래 목록이 밀렸습니다(북마크 0.059 · 스크랩 0.073).

- Lighthouse는 쿠키를 요청 머리글(`--extra-headers`)로만 넣을 수 있습니다. 화면 쪽 JS는 브라우저 쿠키(`logged_in`)로 로그인 여부를 정하므로, Lighthouse로는 로그인 안 된 빈 틀이 재집니다. 그래서 Playwright로 쿠키를 넣고 `largest-contentful-paint` · `layout-shift`를 직접 기록했습니다.

## 측정 방법

Lighthouse 13.6(`npx -y lighthouse@13.6.0`), 모바일 기본값(화면 412px · CPU 4배 느리게 · 느린 4G), 성능 항목만, 화면마다 3번.

| 방식 | 옵션 | 어떻게 재나 | 쓸 때 |
| --- | --- | --- | --- |
| 계산으로 흉내 | 기본 (`--throttling-method=simulate`) | 빠른 회선으로 한 번 열고, 그 기록으로 느린 휴대폰을 **계산**. LCP 전에 받은 요청은 모두 LCP에 필요했던 것으로 봄 | PageSpeed Insights · DevTools 기본과 같은 숫자. 흔들림이 큼 |
| 실제로 느리게 | `--throttling-method=devtools` | 회선 1.6 Mbps · 지연 150ms · CPU 4배를 **실제로** 걸고 열어 브라우저가 기록한 값 | 실제 휴대폰 Chrome에 가까움. 원인 찾기 |

```bash
CHROME_PATH=".../Google Chrome for Testing" npx -y lighthouse@13.6.0 https://newpick.hyeoniverse.com/about \
  --only-categories=performance --throttling-method=devtools \
  --blocked-url-patterns='*viewcount*' --output=json --output-path=about-1.json \
  --chrome-flags="--headless=new --no-sandbox"
```

- `--blocked-url-patterns='*viewcount*'`: 재는 동안 운영 조회수를 올리지 않게.
- 원인 찾기는 Lighthouse만으로는 잘 안 됐습니다. Playwright로 같은 조건(CDP `Network.emulateNetworkConditions` · `Emulation.setCPUThrottlingRate`)을 걸고 `PerformanceObserver`(`largest-contentful-paint` · `layout-shift`)와 `MutationObserver`(요소가 다시 만들어지는지)를 같이 기록해, 무엇을 끄면 LCP가 언제로 바뀌는지 하나씩 비교했습니다.
- 로컬 운영 빌드 비교는 `next build` 두 개(main · 브랜치)를 같은 기계에서 하나씩 `next start`로 띄워 쟀습니다. 로컬은 응답 지연이 거의 없어, 운영에서만 드러나는 것(#302의 서버 시간대)이 있습니다.

## 남은 것

- **목록의 "계산으로 흉내" LCP 3.7초**: LCP는 큰 배너의 첫 카드 사진(Naver)입니다. "실제로 느리게"로는 1.8초라 계산 방식의 몫이 큽니다.
- 홈 사진 띠가 보이는 동안 계속 사진을 받는 것(위 점수 없음의 까닭)은 띠가 흐르는 한 자연스러운 동작이라 그대로 둡니다.
